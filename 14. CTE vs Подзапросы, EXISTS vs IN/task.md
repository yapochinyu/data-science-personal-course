

## Ключевые идеи

1. ★ Если две части запроса должны брать строки по одному правилу, я могу описать отбор один раз и дать получившимся строкам имя через `WITH`. Такой **именованный набор строк** называется **CTE**. По имени к нему можно обратиться в пределах того же запроса.
2. ★ Если запрос в скобках читает значение из текущей строки запроса снаружи, его ответ может зависеть от этой строки. Запрос внутри другого запроса — **подзапрос**, а запрос снаружи — **внешний запрос**. Подзапрос, который берёт **значение из текущей строки снаружи**, называется **коррелированным**. Если он берёт **все значения из собственных источников**, он **некоррелированный**.
3. ★ Если мне нужно решить, оставить ли текущую строку, я могу спросить, **совпал ли номер со значением** из списка, через `IN` или **нашлась ли хотя бы одна** подходящая строка через `EXISTS`. Каждая проверка даёт один ответ на исходную строку, даже если подходящих записей несколько.
4. ★ При поиске отсутствующей пары важно, может ли номер быть неизвестен. Если **номер в записи отсутствует**, в SQL на его месте стоит `NULL`. Проверка «**нет совпадающего значения в списке**» (`NOT IN`) может дать «неизвестно», если точного совпадения нет, а справа есть `NULL`. Проверка «**нет ни одной подходящей строки**» (`NOT EXISTS`) даёт «да», если ни одна строка не прошла условие поиска пары.
5. Если справа от сравнения есть **место только для одного значения**, подзапрос в этом месте называют **скалярным**. У него должен быть один столбец. Из одной строки берётся значение, при пустом результате получается `NULL`, а при нескольких строках возникает ошибка, даже если значения одинаковы.
6. Если я составляю **одну строку на каждую пару** записей, прошедшую условие, это `INNER JOIN`. Если у одной исходной строки несколько подходящих пар, в ответе будет по строке на каждую из них.
7. Если я прошу **подсчитать число оставшихся строк** через `COUNT(*)` и вывести только этот общий итог, ответом будет одна строка с числом, даже при пустом отборе. Для проверки наличия строк одна строка с нулём даёт «да».
8. Если я дал промежуточному набору имя, база может подготовить этот набор отдельно или совместить его отбор с другими действиями запроса. **Порядок действий, выбранных базой**, называется **планом выполнения**. По наличию `WITH` я не могу определить, какой вариант отработает быстрее.

## Задачи

### 1. ★ Один отбор на две части отчёта

**Идея 1.** Напиши инструкцию, которая задаёт, какие записи взять и что показать. Такая инструкция называется **запросом**, а **язык, на котором её пишут**, — **SQL**. Во всех задачах данные хранит и **выполняет запросы программа PostgreSQL**.

**Дано.** Записи о заказах собраны в таблицу `orders(order_id, channel, amount)`. Каждая **запись об одном заказе** — строка. Номер заказа, канал и сумма — столбцы, то есть **поля, общие для всех записей**.

`[(11, 'web', 60), (12, 'web', 100), (13, 'app', 300), (14, 'web', 140), (15, 'web', 20)]`

**Что должно получиться.** Верни `order_id` и `amount` для заказов из `web` на сумму от 60 включительно, которые строго дороже среднего по этим же заказам. Чтобы найти среднее, нужно **сложить суммы и разделить на** число сумм. В SQL это делает `AVG`. Сам проверяемый заказ тоже входит в расчёт среднего.

**Пример «вход → выход».** `[(1, 'web', 60), (2, 'web', 80), (3, 'web', 100), (4, 'app', 200)]` → `[(3, 100)]`.

**Ограничение.** Запиши правила про канал и порог один раз через `WITH`. Порядок строк в ответе любой. Вслух объясни, что произойдёт, если после этого запустить отдельный запрос, который попытается прочитать строки по имени, объявленному в `WITH`.

> [!hint]- Подсказка 1  
> Сначала определи, какие заказы вообще входят в отчёт. Эти же заказы нужны и для сравнения, и для расчёта среднего. Здесь работает идея 1.

> [!hint]- Подсказка 2  
> Представь, что ты записал порог в двух местах и потом поднял его только там, где выбираешь заказы для вывода. Один список изменится, а второй останется прежним. Проследи, на каком шаге заказ может исчезнуть из первого списка и всё ещё влиять на среднее.

> [!hint]- Подсказка 3  
> Дай имя отобранным заказам. Возьми из этого набора строки для проверки. Отдельно прочитай тот же набор внутри скобок, получи одно среднее и сравни с ним сумму каждой проверяемой строки.

### 2. ★ Для каждого покупателя своё среднее

**Идея 2.**

**Дано.** В `orders(order_id, user_id, amount)` лежат номер заказа, номер покупателя и сумма. Все значения известны.

`[(21, 7, 40), (22, 7, 100), (23, 8, 80), (24, 8, 120), (25, 9, 50)]`

**Что должно получиться.** Напиши SQL, который возвращает `order_id` и `amount` для заказов строго дороже среднего заказа **того же покупателя**. В среднее включай все заказы этого покупателя, в том числе тот, который проверяешь.

**Пример «вход → выход».** `[(1, 10, 20), (2, 10, 60), (3, 20, 100), (4, 20, 140)]` → `[(2, 60), (4, 140)]`. В примере первые два заказа сравниваются со средним 40, последние два — со средним 120.

**Ограничение.** Используй коррелированный подзапрос. Порядок ответа любой. Вслух пройди по своему запросу для заказов `22` и `23`. Назови номер, который приходит снаружи, и выпиши суммы, которые остаются внутри. Затем объясни, что изменится, если по обе стороны сравнения номеров случайно взять номер из одной внутренней строки.

> [!hint]- Подсказка 1  
> Для текущего заказа спроси, дороже ли он обычного заказа этого покупателя. По идее 2 скобкам нужен номер покупателя из текущей строки снаружи.

> [!hint]- Подсказка 2  
> Возьми два заказа разных покупателей. Если сравнить номер внутренней строки с ним же, смена заказа снаружи никак не изменит отбор внутри. Найди, где должна появиться ссылка на текущий заказ.

> [!hint]- Подсказка 3  
> Дай разные имена заказам снаружи и заказам внутри скобок. Для текущей строки внутри оставь суммы того же покупателя. Получи из них одно среднее, затем снаружи сравни с ним текущую сумму.

### 3. ★ Два способа проверить наличие посещения

**Идея 3.**

**Дано.** В `users(user_id)` три пользователя с разными известными номерами `[31, 32, 33]`. В `visits(user_id, minutes)` записаны номер посетителя и целое число минут.

`[(31, 6), (31, 8), (32, 4), (NULL, 9)]`

**Что должно получиться.** Напиши два запроса, которые возвращают номера пользователей с хотя бы одним посещением от 5 минут включительно. Если у пользователя два подходящих посещения, его номер должен выйти один раз. Для отбора строк по условию используется `WHERE`. В нём **проходит только ответ «да»**. Ответы «нет» и «неизвестно» строку отбрасывают.

**Пример «вход → выход».** Пользователи `[1, 2, 3]`, посещения `[(1, 5), (1, 8), (2, 4)]` → `[1]` в обоих вариантах.

**Ограничение.** В первом запросе используй `IN` с подзапросом, во втором — `EXISTS` с подзапросом. Порядок ответа любой. На исходных данных отдельно назови ответ каждой проверки для пользователя `33`, прежде чем `WHERE` решит, оставить ли строку. Объясни, почему два посещения пользователя `31` не дают две строки на выходе.

> [!hint]- Подсказка 1  
> В первом варианте спроси, есть ли номер в списке. Во втором спроси, есть ли посещение с нужным номером и длительностью. Это два вопроса из идеи 3.

> [!hint]- Подсказка 2  
> Для номера без точного совпадения выпиши ответы на сравнения с известными и неизвестным номерами. Затем отдельно проверь, какие из этих сравнений оставят хоть одну строку посещения внутри скобок.

> [!hint]- Подсказка 3  
> Для первого запроса собери один столбец номеров из достаточно длинных посещений. Для второго возьми текущего пользователя и ищи посещение, которое подходит ему и по номеру, и по длительности. Перед выводом для каждого варианта отметь, какие исходные строки получили «да».

### 4. ★ Кто остался без крупного платежа

**Идея 4.**

**Дано.** В `users(user_id)` лежат разные известные номера `[41, 42, 43]`. В `payments(user_id, amount)` лежат платежи.

`[(41, 150), (42, 90), (NULL, 160), (43, 100)]`

**Что должно получиться.** Напиши SQL, который возвращает номера пользователей, для которых не нашлось ни одного платежа от 100 включительно с тем же номером. У платежа с неизвестным покупателем нет номера, по которому его можно связать с пользователем.

**Пример «вход → выход».** Пользователи `[1, 2, 3]`, платежи `[(1, 110), (2, 80), (NULL, 120)]` → `[2, 3]`.

**Ограничение.** Для рабочего запроса используй `NOT EXISTS`. Порядок ответа любой. Затем вслух разбери попытку использовать `NOT IN` по номерам покупателей из крупных платежей, включая неизвестный номер. Для пользователя `42` выпиши ответы на отдельные сравнения, ответ `IN`, ответ после отрицания и решение `WHERE`. Отрицание в SQL пишут как `NOT`. Оно **меняет «да» на «нет»** и «нет» на «да», а ответ «неизвестно» оставляет прежним.

> [!hint]- Подсказка 1  
> Для каждого пользователя попробуй найти крупный платёж, который можно связать с его номером. По идее 4 важно различать отсутствие найденной строки и ответ «неизвестно» при сравнении со списком.

> [!hint]- Подсказка 2  
> В варианте со списком неизвестный номер доходит до сравнения с номером пользователя. В варианте с поиском строки сравнение сначала должно дать «да» внутри скобок. Проверь, на каком шаге запись с неизвестным номером перестаёт участвовать во второй проверке.

> [!hint]- Подсказка 3  
> Возьми пользователя снаружи. Внутри проверь для каждого платежа сумму и равенство номеров. Для рабочего запроса реши, оставить ли пользователя, по наличию строк после этих двух проверок. Для разбора попытки со списком сначала выпиши номера крупных платежей и только потом применяй отрицание.

### 5. Сколько значений можно поставить справа от сравнения

**Идея 5.**

**Дано.** В `sales(amount)` лежат суммы `[55, 70, 85]`. Запрос оставляет суммы строго выше порога. Справа от `>` стоит подзапрос, который читает единственный столбец `limits(amount)` и берёт из него все строки без изменений.

**Что должно получиться.** Разбери три отдельных запуска, в которых `limits` содержит `[]`, `[70]` и `[70, 70]`. Для каждого скажи, появляется ли ошибка. Если её нет, назови значение справа от `>`, ответ сравнения для суммы `85` и список сумм, которые попадут в вывод.

**Пример «вход → выход».** Продажи `[40, 70, 90]`, пороги `[65]` → справа стоит `65`, сравнение для `90` даёт «да», в выводе `[70, 90]`.

**Ограничение.** Не меняй запрос и не убирай одинаковые строки из `limits`.

> [!hint]- Подсказка 1  
> Знак `>` просит одно значение справа. По идее 5 сначала выясни, что именно вернули скобки, и только затем переходи к сравнению.

> [!hint]- Подсказка 3  
> В каждом запуске выпиши строки из скобок и посчитай их. Реши, можно ли поставить результат справа от `>`. Если сравнение возможно, пройди по суммам слева по одной и примени правило `WHERE`.

### 6. Сколько строк даёт одна пара и сколько даёт проверка

**Идея 6.**

**Дано.** В `users(user_id)` лежат разные номера `[61, 62, 63]`. В `tickets(user_id)` каждая строка — отдельное обращение, а номера в строках такие `[61, 61, 62, 61]`.

**Что должно получиться.** Напиши два запроса. Первый составляет пары «пользователь — обращение» с равными номерами и выводит номер пользователя из каждой пары. Второй проверяет наличие хотя бы одного обращения и выводит номер из каждой прошедшей строки `users`. Вслух назови, что означает одна выходная строка в каждом варианте.

**Пример «вход → выход».** Пользователи `[1, 2, 3]`, обращения `[2, 2, 3]` → первый запрос выдаёт `[2, 2, 3]`, второй — `[2, 3]`.

**Ограничение.** Используй `INNER JOIN` в первом запросе и `EXISTS` во втором. Сохрани все строки, которые вернул каждый вариант. Порядок любой.

> [!hint]- Подсказка 1  
> В первом варианте посчитай, сколько пар удалось собрать. Во втором посчитай, сколько пользователей получили ответ «да». Разница следует из идеи 6.

> [!hint]- Подсказка 3  
> Для первого запроса выпиши для каждого пользователя по паре на каждое обращение с его номером, затем оставь из пар только номера. Для второго пройди по исходным строкам пользователей и для каждой реши, нашлась ли хотя бы одна подходящая строка обращения.

### 7. Одна строка с числом и пустой результат

**Идея 7.**

**Дано.** В `refunds(amount)` лежат суммы возвратов `[12, 35, 50, 80]`. В запросе коллеги проверка `EXISTS` смотрит на результат подзапроса. Тот сначала оставляет возвраты строго больше 100, а затем выводит только общий `COUNT(*)` по оставшимся строкам.

**Что должно получиться.** Вслух назови строки после отбора, строки после подсчёта и ответ `EXISTS`. Затем напиши запрос, который выдаёт один ответ «да» или «нет» на вопрос «есть ли возврат строго больше 100?».

**Пример «вход → выход».** Суммы `[10, 40, 50]`, порог `30` → после отбора `[40, 50]`, после подсчёта `[2]`, проверка наличия строки в результате подсчёта даёт «да».

**Ограничение.** В новом запросе сохрани проверку `EXISTS`. Он должен давать правильный ответ и при пустой таблице, и при наличии возвратов выше порога.

> [!hint]- Подсказка 1  
> Раздели два вопроса. Сколько возвратов прошло отбор? Сколько строк получилось после подсчёта? В идее 7 это разные числа.

> [!hint]- Подсказка 3  
> Выпиши отдельно результат отбора и результат подсчёта. Укажи, какой из этих списков проверяет `EXISTS` в запросе коллеги. Для нового запроса выбери, какой список нужно передать на проверку, чтобы она отвечала именно про возвраты.

### 8. Один запрос, два способа получить ответ

**Идея 8.**

**Дано.** В `stores(store_id)` лежат номера `[11, 12, 13, 14]`. Шаг в `WITH` берёт все номера, итоговый запрос оставляет `store_id = 13`. Рассмотри два возможных способа выполнения:

- А. База подготавливает набор со всеми номерами, затем отбирает нужный номер из этого набора.
- Б. База проверяет номер сразу при чтении и передаёт дальше только прошедшие строки.

**Что должно получиться.** Для каждого способа назови, сколько строк осталось сразу после чтения и до любого отдельного отбора, а затем назови итоговый номер. Ответь на утверждение коллеги «раз написано `WITH`, база обязана действовать способом А». Объясни, что нужно посмотреть, чтобы узнать, какой способ выбрала база.

**Пример «вход → выход».** Номера `[1, 2, 3]`, нужен `2`. Для способа А → после чтения три строки, итог `[2]`. Для способа Б → после чтения одна строка, итог `[2]`.

**Ограничение.** Разбери оба способа вручную. Замерять время не нужно.

> [!hint]- Подсказка 1  
> По идее 8 имя набора помогает читать запрос, а база может получить один и тот же ответ разными способами.

> [!hint]- Подсказка 3  
> Отметь, в какой момент в каждом способе проверяется номер. Выпиши строки, которые уже прочитаны к этому моменту, и отдельно строки итогового ответа. Затем назови, где можно увидеть действия, выбранные базой.

## Проверка терминов

- **Таблица** — «записи о заказах собраны» (задача 1).
- **Строка** — «запись об одном заказе» (задача 1).
- **Столбец** — «поля, общие для всех записей» (задача 1).
- **Запрос** — «какие записи взять и что показать» (задача 1).
- **SQL** — «язык, на котором её пишут» (задача 1).
- **PostgreSQL** — «выполняет запросы программа PostgreSQL» (задача 1).
- **`WITH`** — «дать получившимся строкам имя» (идея 1).
- **CTE** — «именованный набор строк» (идея 1).
- **Подзапрос** — «запрос внутри другого запроса» (идея 2).
- **Внешний запрос** — «а запрос снаружи» (идея 2).
- **Коррелированный подзапрос** — «значение из текущей строки снаружи» (идея 2).
- **Некоррелированный подзапрос** — «все значения из собственных источников» (идея 2).
- **`IN`** — «совпал ли номер со значением» (идея 3).
- **`EXISTS`** — «нашлась ли хотя бы одна» (идея 3).
- **`NULL`** — «номер в записи отсутствует» (идея 4).
- **`NOT IN`** — «нет совпадающего значения в списке» (идея 4).
- **`NOT EXISTS`** — «нет ни одной подходящей строки» (идея 4).
- **Скалярный подзапрос** — «место только для одного значения» (идея 5).
- **`INNER JOIN`** — «одну строку на каждую пару» (идея 6).
- **`COUNT(*)`** — «подсчитать число оставшихся строк» (идея 7).
- **План выполнения** — «порядок действий, выбранных базой» (идея 8).
- **`AVG`** — «сложить суммы и разделить на» (задача 1).
- **`WHERE`** — «проходит только ответ «да»» (задача 3).
- **`NOT`** — «меняет «да» на «нет»» (задача 4).

**Для каждой задачи открывай отдельный fiddle**, поскольку названия некоторых таблиц повторяются.

Во всех скриптах `CREATE TABLE` создаёт таблицу с перечисленными полями, а `INSERT INTO … VALUES` добавляет записи. Тип `integer` хранит целые числа, `text` — текст. `PRIMARY KEY` требует уникального и известного номера записи. `NOT NULL` требует заполненного значения, а без этого ограничения поле может содержать `NULL`.

### 5. Сколько значений можно поставить справа от сравнения

Для этой задачи нужны три отдельных запуска. Сначала вставь основную заготовку.

```sql
CREATE TABLE sales (
    amount integer NOT NULL
);

CREATE TABLE limits (
    amount integer NOT NULL
);

INSERT INTO sales (amount)
VALUES
    (55),
    (70),
    (85);
```

**Первый запуск** — используй заготовку как есть. Таблица `limits` пустая.

**Второй запуск** — добавь в конец заготовки следующую команду.

```sql
INSERT INTO limits (amount)
VALUES
    (70);
```

**Третий запуск** — вместо команды второго запуска добавь эту.

```sql
INSERT INTO limits (amount)
VALUES
    (70),
    (70);
```

Здесь у `limits.amount` разрешены одинаковые значения, чтобы проверить случай с двумя одинаковыми строками.

## Проверка терминов

- **`CREATE TABLE`** — «создаёт таблицу с перечисленными полями».
- **`INSERT INTO … VALUES`** — «добавляет записи».
- **`integer`** — «хранит целые числа».
- **`text`** — «текст».
- **`PRIMARY KEY`** — «уникального и известного номера».
- **`NOT NULL`** — «требует заполненного значения».
- **`NULL`** — «поле может содержать `NULL`».
