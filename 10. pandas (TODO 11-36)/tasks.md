## Ключевые идеи

1. **Массив — это одинаковые по размеру элементы одного типа, лежащие в памяти впритык.** Адрес любого элемента вычисляется как `начало + размер × номер`: одно умножение и одно сложение, независимо от номера. Питоновский список устроен иначе — он хранит адреса объектов, разбросанных по памяти, и каждый доступ требует прыжка по указателю плюс чтения заголовка.
    
2. **Процессор тянет из памяти не байт, а кусок в 64 байта, который оседает в кэше.** Поэтому данные, лежащие подряд, приезжают пачкой, а прыжки по разбросанным адресам — это сотни тактов вместо единиц на каждое обращение. Это даёт разницу в десятки раз ещё до всякой диспетчеризации по типу.
    
3. **dtype — это описание «что за элементы внутри и сколько каждый занимает», записанное один раз на весь массив, а не в каждый элемент.** Всё, кроме `object`, — быстрый вариант с данными впритык; `object` — массив указателей, то есть тот же питоновский список с прыжками.
    
4. **Векторизация — это не «отсутствие слова `for` в моём коде», а «цикл по элементам выполняется внутри скомпилированного кода, а Python делает ровно один вызов».** Главная метрика скорости pandas — не количество арифметических операций, а количество возвратов управления в интерпретатор.
    
5. **Срез массива бывает представлением (та же память, новая шапка) или копией (новая память), и по виду кода это неотличимо.** Представление возможно только когда нужные элементы лежат регулярно — подряд или с постоянным шагом; произвольный список номеров и булева маска обязаны дать копию.
    
6. **Series — это ndarray плюс индекс с подписями, а индекс лениво строит рядом с собой хеш-таблицу.** Поэтому поиск по метке не зависит от размера таблицы: посчитать хеш, взять остаток от деления на число корзин, сходить в корзину.
    
7. **DataFrame хранится по столбцам, а столбцы одного dtype склеены в один непрерывный блок; сверху сидит BlockManager с таблицей соответствия «столбец → блок и позиция».** Отсюда: операция над столбцом дёшева, а строки как связного объекта в памяти не существует.
    
8. **Дописать столбец в конец блока нельзя — сразу за блоком лежат чужие данные.** Любое добавление столбца перевыделяет блок и копирует всё старое, поэтому добавление столбцов в цикле стоит квадрат, а не линию; то же с `pd.concat` в цикле.
    
9. **В `int64` нет ни одной свободной комбинации битов под «пусто», а в `float64` она есть — это NaN.** Поэтому пропуск в целочисленном столбце превращает весь столбец в `float64`, и целые больше 2^53 при этом молча портятся. Типы с маской (`Int64`, `boolean`) хранят пропуск отдельным массивом-отметчиком и целые не ломают.
    
10. **`NaN` не равен ничему, включая себя, и любое сравнение с ним даёт `False` — то есть при фильтрации библиотека молча решает за тебя «не брать».** `pd.NA` вместо этого даёт третье состояние «неизвестно» и заставляет решить явно через `.fillna(False)`; при этом «неизвестно» заражает результат не всегда: `pd.NA | True` = `True`, `pd.NA & False` = `False`.
    
11. **Перед любой бинарной операцией pandas выравнивает операнды по меткам индекса, а не по позициям.** Строится объединение меток, каждый операнд раскладывается по нему, недостающие места становятся NaN. Отсюда молчаливые NaN после фильтрации (в индексе дырки) и при присваивании Series в столбец.
    
12. **`loc` ищет метку в хеш-таблице и включает правую границу среза; `iloc` берёт n-й по порядку и правую границу не включает.** Включённая граница у `loc` — не каприз: у меток нет арифметики, и при исключённой границе пришлось бы писать метку следующего элемента, то есть знать содержимое до того, как режешь.
    
13. **`groupby` не сортирует и не создаёт подтаблицы.** Первый проход — факторизация через хеш-таблицу, получаем массив кодов; второй проход — идём по значениям и кодам одновременно, прибавляя каждое значение в свою ячейку массива-накопителя. Оба прохода — скомпилированный код.
    
14. **Быстрый путь groupby существует только для конечного списка готовых агрегатов.** Своя функция через `apply`/`agg(lambda)` заставляет pandas физически собрать объект Series на каждую группу и вернуть управление в Python — на 200 тысячах групп это минуты вместо миллисекунд.
    
15. **`agg` даёт одно значение на группу, `transform` — столько же значений, сколько строк на входе, разложенных обратно по исходным позициям, `filter` выбрасывает целые группы.** Результат `transform` можно сразу присвоить в столбец без всякого соединения — он уже нужной длины и в нужном порядке.
    
16. **`merge` — это соединение через хеш-таблицу: один проход строит соответствие по правой таблице, второй ищет в нём для каждой строки слева.** Если ключ справа не уникален, одна строка слева даёт столько строк, сколько совпадений справа — 3 × 4 = 12, и на миллионах это взрыв памяти.
    
17. **Несовпадение типов ключей при merge не даёт ошибки — оно даёт молча пустой результат.** А `indicator=True` добавляет столбец `_merge` со значениями `both` / `left_only` / `right_only`, который за один вызов отвечает, сколько строк не нашло пару, и отличает «не нашли пользователя» от «нашли, но поле пустое».
    
18. **В SQL строки с NULL в ключе не соединяются ни с чем, а в pandas NaN соединяется с NaN.** Потому что pandas сравнивает ключи не оператором равенства, а через хеш-таблицу, куда NaN попадает как обычное значение и находит там своего близнеца — отсюда неочевидное раздувание.
    
19. **`category` — это словарь уникальных значений плюс массив маленьких целых кодов.** Он окупается, когда уникальных на порядки меньше, чем строк: сравнение со строкой превращается в сравнение целых, группировка пропускает шаг факторизации. При высокой кардинальности (идентификаторы) он делает только хуже: словарь всё равно хранит все строки, а сверху добавляется хеш-таблица.
    
20. **У двух категориальных столбцов с разными словарями код 0 означает разное, поэтому `concat` и `merge` не могут состыковать коды и откатывают тип к `object` — молча, без ошибки.** Лечится заранее заданным общим `CategoricalDtype` или `union_categoricals`.
    
21. **Обычная категория отказывается сравниваться на «больше/меньше», потому что порядок кодов — техническая деталь, а не свойство данных.** Порядок задаётся явно через `ordered=True`, и тогда сравнение становится быстрой арифметикой над кодами. А присваивание значения, которого нет в словаре, падает — кода для него не существует.
    
22. **`datetime64[ns]` — это `int64` с числом наносекунд от полуночи 1 января 1970.** Поэтому разница дат — вычитание целых, сортировка — сортировка целых. Платa: наносекундная точность в 8 байтах покрывает примерно 1677–2262 годы.
    
23. **`.str` и `.dt` — это цикл на C, но `.str` внутри цикла всё равно зовёт питоновский строковый метод на каждый элемент.** Поэтому `.dt` — настоящая арифметика над целыми, а `.str` быстрее `apply` всего в 2–5 раз, а не в тысячу.
    
24. **`sort_values` вычисляет массив перестановки, а потом применяет его к каждому столбцу отдельно копированием по списку позиций.** Дорого по трём причинам сразу: копируется вся таблица (двойной пик памяти), чтение идёт вразнобой мимо кэша, работа умножается на число столбцов. Отсюда: отбирать нужные столбцы до сортировки, а не после.
    
25. **`nlargest(k)` делает один проход, держа структуру на k элементов с мгновенно доступным минимумом: большинство значений отсеивается одним сравнением.** Это `n` сравнений вместо `n log n` плюс копирование в конце только k строк вместо всей таблицы.
    
26. **Стабильная сортировка сохраняет исходный взаимный порядок при равных ключах, а по умолчанию в pandas сортировка нестабильна.** Поэтому «отсортировать по A, потом по B» через два вызова — ненадёжно; сортировать надо по списку ключей за один вызов, тогда порядок определён однозначно.
    
27. **`rolling` считает по порядку строк, а не по датам, и включает текущую строку в окно.** Для признака это значит два обязательных шага: сортировка по времени и `shift(1)` перед окном, иначе в признак заезжает сама целевая строка.
    
28. **`center=True` берёт значения справа от текущей позиции — то есть из будущего — и при этом выглядит абсолютно нормально: пропусков нет, качество на проверке отличное.** Для сглаживания графика это уместно, для признаков модели — никогда.
    
29. **Сумма и среднее в окне считаются скользящим накопителем («предыдущая сумма + новое − выбывшее»), поэтому стоят одинаково при окне в 3 и в 300.** Медиана, квантиль и число уникальных так не пересчитываются — их стоимость растёт с размером окна.
    
30. **`ewm` убирает обрыв жёсткого окна: `результат = alpha × текущее + (1−alpha) × предыдущий результат`.** Вес старого значения падает в геометрической прогрессии, но никогда не обнуляется — значит нет искусственного скачка в день, когда значение вышло из окна, и памяти нужно O(1).
    
31. **MultiIndex — это та же факторизация, только по нескольким столбцам сразу: список `levels` со словарями уникальных значений и список `codes` с массивами кодов на каждый уровень.** Не «массив пар строк» — потому что пара строк это два питоновских объекта на каждую строку таблицы.
    
32. **`loc` для MultiIndex читает метки слева направо, поэтому по нижнему уровню он искать не умеет — для этого есть `xs` с явным указанием уровня.** А на неотсортированном MultiIndex поиск идёт проходом по всему массиву кодов; после `sort_index()` одинаковые коды лежат подряд и границы находятся двоичным поиском.
    
33. **`pivot` только перекладывает значения по ячейкам и падает при дубликате пары (строка, столбец), потому что не умеет выбирать между двумя значениями.** `pivot_table` — это группировка плюс перекладка, дубликаты исчезают по построению, но агрегат по умолчанию — среднее, так что он молча усреднит незамеченные дубликаты.
    
34. **Размер результата `unstack` равен произведению числа уникальных по строкам на число уникальных по столбцам и никак не связан с числом исходных строк.** Прямоугольная таблица не умеет хранить дырки — под каждую пару выделяется ячейка. Прикидка заранее: `nunique() × nunique() × 8` байт.
    
35. **`duplicated` — один проход с множеством уже виденных значений, а по нескольким столбцам pandas факторизует каждый столбец отдельно и склеивает коды позиционной арифметикой.** Никаких кортежей-объектов: поиск идёт по одному массиву целых.
    
36. **`keep='first'` оставляет строку, которая стоит первой в текущем порядке строк, — не «самую свежую» и не «самую правильную».** Поэтому сортировка перед `drop_duplicates` — это часть логики, а не оптимизация; без неё код даёт разный ответ на разных выгрузках одних и тех же данных и никогда не падает.
    
37. **Технический дубль (совпадение по всем столбцам) удаляется смело, бизнес-дубль (одна сущность, разные значения) требует решения, которое никакая функция за тебя не примет.** Поэтому сначала смотреть на них через `keep=False`, и только потом решать.
    
38. **Утечка — это не «целевая переменная в признаках», а «информация, которой в момент предсказания ещё не существует».** Три двери в pandas: агрегаты по всей таблице до разделения, заполнение пропусков и нормализация статистикой по всей таблице, признаки-накопители по всей истории вместо только прошлого.
    
39. **Дубликаты и способ деления — это четвёртая дверь для утечки, которую не закрывает ни один pipeline.** Копии строки растаскиваются по обе стороны случайным делением, а один пользователь с полусотней строк оказывается и в обучении, и в проверке — модель выучивает конкретного пользователя, а проверяют её на нём же.
    
40. **Защита pipeline структурна, а не дисциплинарна: `fit` смотрит и запоминает, `transform` только применяет запомненное.** Посчитать медиану по проверочной выборке невозможно не потому, что я об этом помню, а потому, что такого действия нет в интерфейсе предсказания. Но pipeline не знает, откуда взялись числа, которые я посчитал раньше в pandas.
    
41. **`SettingWithCopyWarning` — это сообщение о неопределённости, а не о стиле: запись идёт в объект, который может быть копией среза.** Правило: если слева от знака равенства больше одной пары квадратных скобок — это ошибка, всё должно уместиться в одно обращение через `.loc`.
    
42. **`inplace=True` означает «результат присвоится обратно в ту же переменную», а не «изменения произойдут прямо в существующих байтах».** Внутри всё равно строится новый набор блоков, пик памяти тот же, зато цепочка ломается и `df = df.dropna(inplace=True)` превращает `df` в `None`.
    
43. **Parquet умеет не читать данные благодаря двум вещам сразу: данные лежат по столбцам, и в хвосте файла записаны минимум и максимум по каждой группе строк.** Пропуск групп работает только если данные отсортированы или сгруппированы по столбцу фильтра — иначе в каждой группе минимум и максимум охватывают весь диапазон.
    
44. **Партиционирование выносит значение в имя папки, так что столбца внутри файлов нет и ненужные папки не открываются вовсе.** Платa — накладные расходы на каждый файл: разбиение по часу даёт тысячи крошечных файлов, и чтение становится медленнее, чем из одного большого.
    
45. **Чтение pickle — это выполнение записанных в файле команд, поэтому открыть чужой pickle равносильно запуску присланного скрипта.** Плюс привязка к версиям библиотек и нечитаемость чем-либо кроме Python.
    
46. **Ячейка, которая меняет объект на месте, зависит от истории нажатий, а не только от кода.** `df3['revenue'] = df3['revenue'] * 1.2` при повторном запуске даёт другие числа и никогда не падает. Цепочка вызовов идемпотентна по построению и попутно освобождает промежуточные результаты сразу.
    
47. **`assign` с лямбдой видит таблицу в этой точке цепочки, а не исходный `df`, и аргументы применяются по порядку — поэтому следующий столбец может опираться на созданный строкой выше.** Ссылка на исходный `df` внутри цепочки даст расхождение длин и месиво из NaN по механизму выравнивания.
    
48. **`apply(axis=1)` — самый дорогой вариант именно потому, что данные хранятся по столбцам: чтобы отдать строку, pandas на каждой итерации собирает новый объект Series из разных блоков, приводя всё к общему типу.** `Series.apply` дешевле (не собирается Series), `df.apply(axis=0)` вообще нормален — там вызовов столько, сколько столбцов.
    
49. **Первым делом — измерить.** Бывает, что `apply` на десяти тысячах строк укладывается в 50 миллисекунд и оптимизировать там нечего, а всё время уходит в `merge`, который раздул таблицу в сорок раз.

### Задача 1 (идея 1, 2, 4)

Напиши две функции, вычисляющие поэлементную сумму двух последовательностей длины `n`:

```python
def sum_loop(a: list[int], b: list[int]) -> list[int]: ...
def sum_vec(a: np.ndarray, b: np.ndarray) -> np.ndarray: ...
```

`sum_loop` — чистый Python со списками. `sum_vec` — numpy, ровно одна операция над массивами. Затем измерь обе на `n = 1_000_000` через `time.perf_counter` и выведи отношение времён.

Пример на 3 элементах: `a=[1,2,3]`, `b=[10,20,30]` → обе возвращают `[11,22,33]`.

Ограничение: в `sum_vec` запрещены `for`, `map`, списковые включения и `np.vectorize`.

> [!hint]- Подсказка 1  
> Здесь проверяется идея 4: считать надо не количество сложений (оно одинаково), а количество раз, когда управление возвращается в интерпретатор. В первой функции — миллион возвратов, во второй должен быть один.

> [!hint]- Подсказка 2  
> В первом случае каждое число — отдельный объект с заголовком, лежащий где-то в памяти; список хранит только адреса. На каждый элемент: сходить по адресу, прочитать заголовок, выбрать операцию по типу, сложить, выделить память под новый объект-результат. Во втором случае тип записан один раз в шапке массива, данные лежат впритык, кэш подтягивает их пачками по 64 байта.

> [!hint]- Подсказка 3  
> Шаг 1: `sum_loop` — обычный проход по индексам с накоплением в список. Шаг 2: `sum_vec` — одна строка, оператор сложения над двумя массивами. Шаг 3: замерить каждую отдельно, засекая время до и после, и поделить одно на другое. Шаг 4: прогнать один раз вхолостую перед замером, чтобы первый вызов не попал в измерение.

### Задача 2 (идея 1, 3)

Дан список из миллиона небольших целых. Напиши функцию, которая возвращает кортеж из двух чисел: сколько байт занимает этот список вместе со всеми объектами внутри, и сколько байт занимает эквивалентный `np.array` с `dtype=int64`.

```python
def compare_size(values: list[int]) -> tuple[int, int]: ...
```

Пример на 5 элементах `[10,20,30,40,50]`: результат вида `(отчёт_для_списка, 40)` — второе число это `5 × 8`.

> [!hint]- Подсказка 2  
> Соблазн считать, что ветвление «если — то — иначе» обязательно требует цикла. Это не так: условие целиком считается одним проходом как массив из «правда/ложь», а потом одним проходом собирается результат. Два условия соединяются поэлементно, но каждое подусловие надо взять в скобки — иначе приоритет операций даст не то. И вторая часть задачи важнее первой: бывает, что это применение функции укладывается в доли секунды, а всё время уходит в соединение, раздувшее таблицу.
