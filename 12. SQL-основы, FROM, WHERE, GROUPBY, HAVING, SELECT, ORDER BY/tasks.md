
## Ключевые идеи

1. SQL описывает, **что** нужно получить, а не **как** это делать. Способ поиска выбирает сама СУБД. Результат любого запроса тоже таблица, поэтому его можно использовать как исходную таблицу для другого запроса (подзапрос).
2. У строк в таблице нет встроенного порядка. Без `ORDER BY` строки приходят в любом порядке, и от запуска к запуску он может меняться. `LIMIT N` без `ORDER BY` вернёт «какие-то N строк», а не «первые».
3. WHERE проверяет каждую строку отдельно и ничего не знает про соседние строки. Поэтому в WHERE невозможно условие «про сумму по городу».
4. `AND` выполняется раньше `OR`, как умножение раньше сложения. Если нужен другой порядок, ставь скобки.
5. ★ GROUP BY раскладывает строки по кучкам с одинаковым значением выбранного столбца. Дальше по запросу идут уже не строки, а кучки, и каждая кучка превращается ровно в одну строку результата.
6. ★ При GROUP BY в SELECT можно писать только столбцы из GROUP BY (внутри кучки у них одно значение по построению) и агрегатные функции (они сворачивают много значений в одно). Для любого другого столбца в одной ячейке результата оказалось бы несколько кандидатов, и правила выбора между ними нет, поэтому PostgreSQL выдаёт ошибку. Старый MySQL без строгого режима молча подставляет значение из случайной строки.
7. ★ Если агрегатная функция есть, а GROUP BY нет, вся таблица считается одной кучкой, и результат состоит из одной строки.
8. ★ Логический порядок выполнения: FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT. Он отвечает на вопрос «что видно на этом шаге»: каждому шагу доступно только то, что посчитали предыдущие.
9. ★ Агрегат нельзя писать в WHERE: на этом шаге кучек ещё нет, и у отдельной строки нет «количества» или «суммы по группе». HAVING выполняется после раскладки и решает судьбу кучки целиком.
10. ★ Алиас создаётся на шаге SELECT. Поэтому по стандарту его не видно в WHERE и HAVING, которые идут раньше, но видно в ORDER BY, который идёт позже. Обойти можно двумя способами: повторить выражение целиком или завернуть запрос в подзапрос. ClickHouse разрешает алиасы и в WHERE, это его расширение. MySQL разрешает их в HAVING.
11. ★ WHERE меняет состав кучек: выброшенная строка не попадёт ни в одну сумму. HAVING состав не трогает: кучка либо остаётся со всеми своими строками, либо исчезает. Поэтому похожие условия в WHERE и в HAVING дают разные числа.
12. Условие, которое можно проверить по одной строке, пиши в WHERE. Тогда лишние строки выкидываются раньше, и группировать приходится меньше.
13. Логический порядок не описывает, что СУБД делает в какую миллисекунду. Оптимизатор может физически менять последовательность действий, но результат обязан совпасть с логическим порядком.
14. ★ NULL означает «значение неизвестно». Это не ноль (ноль — это знание) и не пустая строка.
15. ★ Любое сравнение с NULL (`=`, `<>`, `>`, …) даёт UNKNOWN. WHERE оставляет строку только при TRUE, поэтому FALSE и UNKNOWN одинаково её выкидывают. Проверить, стоит ли в ячейке NULL, можно только через `IS NULL` / `IS NOT NULL`.
16. ★ Трёхзначную логику не нужно зубрить, её можно вывести. Представь, что UNKNOWN может оказаться и TRUE, и FALSE. Если итог от этого не зависит, итог известен. Если зависит, итог UNKNOWN.
17. ★ Строки с NULL тихо пропадают из любого условия на этот столбец, даже из «не равно» и даже из «`> 250 OR <= 250`». Если они нужны, дописывают `OR столбец IS NULL`.
18. Любая арифметика с NULL даёт NULL.
19. ★ Все агрегатные функции, кроме `COUNT(*)`, пропускают NULL. `COUNT(*)` считает строки, `COUNT(столбец)` считает строки, где в этом столбце не NULL, `COUNT(DISTINCT столбец)` считает разные значения без NULL.
20. ★ `AVG(amount)` делит на число известных значений, а `SUM(amount) / COUNT(*)` делит на все строки. Какое из двух чисел правильное, зависит от смысла NULL в данных. Если NULL значит «денег не было», правильно `COALESCE(amount, 0)`. Если NULL значит «данные потерялись», честнее пропустить такие строки.
21. В PostgreSQL деление целого на целое отбрасывает дробь. Для долей пишут `* 1.0`.
22. `SUM` по пустому набору строк даёт NULL, а `COUNT` даёт 0. Если при этом есть `GROUP BY`, кучек не будет вовсе, и запрос вернёт ноль строк.
23. При сравнении через `=` NULL считаются разными, а при группировке и DISTINCT одинаковыми: все NULL попадают в одну кучку. Так договорились в стандарте.
24. В PostgreSQL при `DESC` NULL встаёт в начало, в MySQL в конец. Положение задают явно: `NULLS LAST`.
25. В ClickHouse NULL хранится только в столбцах типа `Nullable(...)`. В остальных вместо «неизвестно» лежит 0 или пустая строка, и AVG эти нули учитывает.
26. ★ `x IN (a, b)` — это ровно `x = a OR x = b`. `x NOT IN (a, b)` — это `x <> a AND x <> b`. Один NULL в списке NOT IN даёт для каждой строки UNKNOWN или FALSE, TRUE не получает никто, и результат пуст.
27. ★ IN с тем же списком работает нормально: в цепочке OR одного TRUE достаточно, и UNKNOWN рядом ничего не портит.
28. ★ Починить NOT IN можно двумя способами. Первый: дописать в подзапрос `WHERE user_id IS NOT NULL`. Второй: переписать на `NOT EXISTS`. EXISTS спрашивает только «нашлась ли хоть одна строка». Строка с NULL даёт UNKNOWN в условии `=` и просто не берётся, остальным строкам она не мешает.

### ★ Задача 2. Почини четыре сломанных запроса (идеи 6, 8, 9, 10)

**Дано:** четыре запроса к `orders`. Каждый из них в PostgreSQL падает с ошибкой.

```sql
-- (а) заказы, у которых сумма со скидкой 20% больше 300
SELECT order_id, amount * 0.8 AS discounted
FROM orders
WHERE discounted > 300;

-- (б) для каждого города — сколько в нём разных покупателей
SELECT city, user_id, COUNT(*)
FROM orders
GROUP BY city;

-- (в) города с выручкой больше 500
SELECT city, SUM(amount) AS revenue
FROM orders
WHERE SUM(amount) > 500
GROUP BY city;

-- (г) города, где хотя бы 2 заказа
SELECT city, COUNT(*) AS cnt
FROM orders
GROUP BY city
HAVING cnt >= 2;
```

**Нужно:** для каждого запроса:

1. назвать шаг логического порядка, на котором он ломается;
2. объяснить, чего на этом шаге ещё нет или что там неоднозначно;
3. переписать запрос так, чтобы он делал то, что сказано в комментарии.

**Пример «вход → выход»** (что должны вернуть исправленные запросы, порядок строк не важен):

- (а) → `order_id`: 1 (400), 3 (560)
- (б) → Москва 2, Казань 1, Сочи 1
- (в) → Москва 800, Казань 900
- (г) → Москва 3, Казань 2

**Ограничения:**

- Только стандартное поведение PostgreSQL, без расширений ClickHouse и MySQL.
- Запрос (а) почини **двумя** способами.
- Вслух скажи, какой из четырёх запросов прошёл бы в MySQL, а какой в ClickHouse, и почему.

> [!hint]- Подсказка 1  
> Каждая ошибка — это попытка использовать то, что на текущем шаге ещё не посчитано или имеет несколько значений. Работают идеи 8 (что видно на каком шаге), 6 (что можно писать в SELECT при группировке), 9 (агрегат в WHERE) и 10 (алиасы).

> [!hint]- Подсказка 2  
> Пройди по порядку FROM → WHERE → GROUP BY → HAVING → SELECT и для каждого запроса отметь, когда появляется нужное ему имя или число. Алиас появляется только на шаге SELECT, а WHERE и HAVING идут раньше. Агрегат появляется только после раскладки, а WHERE идёт до неё. В (б) в кучке «Москва» три строки с `user_id` 10, 10, 30, а ячейка в результате одна. К тому же в комментарии просят не «какой пользователь», а «сколько разных».

> [!hint]- Подсказка 3  
> (а) Способ 1: подставь в фильтр выражение целиком, его можно посчитать по одной строке. Способ 2: внутренний запрос, который создаёт столбец со скидкой, дай ему имя и фильтруй снаружи. (б) Убери из SELECT столбец, у которого в кучке несколько значений, и посчитай разные значения нужной функцией. (в) Перенеси условие на шаг, который работает с кучками. (г) Замени имя на выражение, которое за ним стоит. После каждого исправления прогони запрос руками и сверь с примером.

### Задача 5. Трёхзначная логика на Python (идеи 15, 16, 26)

**Дано:** в Python логические значения TRUE и FALSE — это `True` и `False`. Отметку UNKNOWN (и NULL в данных) обозначим значением `None`. Нужно написать функции:

```python
def sql_eq(a, b):          # сравнение a = b по правилам SQL
def sql_not(a):            # NOT
def sql_and(a, b):         # AND
def sql_or(a, b):          # OR
def sql_not_in(x, values): # x NOT IN (values)
def where_filter(rows, cond):  # оставить элементы rows, для которых cond(элемент) вернула True
```

Здесь `cond` — функция, которая по элементу возвращает `True`, `False` или `None`.

**Нужно:** функции должны вести себя как SQL.

**Пример «вход → выход»:**

```
sql_eq(5, None)               → None
sql_and(True, None)           → None
sql_and(False, None)          → False
sql_or(True, None)            → True
sql_not(None)                 → None
sql_not_in(10, [30, None])    → None
sql_not_in(30, [30, None])    → False
sql_not_in(10, [30])          → True
where_filter([10, 20, 30, 40, 50], cond) → []    # cond(u) = sql_not_in(u, [30, None])
```

**Ограничения:**

- В `sql_and` и `sql_or` нельзя перебирать все 9 сочетаний через `if` или таблицу-словарь. Используй правило из идеи 16: если аргумент неизвестен, подставь вместо него по очереди `True` и `False` и посмотри, совпали ли итоги.
- `sql_not_in` строится только из `sql_eq`, `sql_not` и `sql_and`, без оператора `in` по списку.
- `where_filter` должна оставлять элемент только при `True`, то есть не через проверку «не False».

> Ты программируешь то, что СУБД делает внутри WHERE: сравнение с неизвестным, склейку условий и фильтр, который пропускает только TRUE. Работают идеи 15, 16 и 26.

> [!hint]- Подсказка 3
> 
> 1. Сравнение: если хоть одна сторона неизвестна, ответ «неизвестно», иначе обычное равенство. 2) NOT: неизвестное остаётся неизвестным, остальное переворачивается. 3) AND и OR: если оба аргумента известны, посчитай обычно.
